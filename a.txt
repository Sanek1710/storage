Structural Similarity with Graph Matching:

If neural networks and training are off the table for generating AST embeddings, we can consider alternative approaches for representing ASTs as embeddings or vectors to enable similarity searches. Here are some strategies that can work well without any deep learning models:

1. Handcrafted Feature Vectors
Structural Features: Generate feature vectors based on structural properties of ASTs, such as node counts, depth, and branching factors.
Token-Based Features: Count specific token types (e.g., keywords, operators) and use these counts to form a feature vector.
Frequency of Patterns/Subtrees: Count frequent small subgraphs or patterns within the AST, and use these counts as vector features.
These approaches capture meaningful characteristics of the ASTs, allowing a degree of similarity comparison between different ASTs based on structural or syntactic patterns.

2. Graph Fingerprinting or Hashing Techniques
MinHashing or SimHash: Convert each AST into a "fingerprint" or hash that represents its structural characteristics. For instance, you could use hashing on node sequences or small subtrees.
Tree Edit Distance (TED): Compute distances between trees by counting the minimum edit operations (insertions, deletions, substitutions) needed to transform one tree into another. Although it’s more computationally intensive, TED can capture structural similarities effectively.
Using these hashing techniques, you can produce compact representations of each AST and then store them in a searchable data structure (like a locality-sensitive hashing index) to find similar fingerprints.

3. Shingling (Subtree-Based Features)
Subtree Shingling: Decompose each AST into smaller subtrees or subgraphs (e.g., up to a fixed depth) and represent each subtree as a "shingle." Count the occurrences of these subtrees to build a vector representation.
Bag of Subtrees (BoS): Construct a vector by counting how many times each type of subtree appears within an AST. This "bag of subtrees" representation can provide a fixed-length vector that captures common structures within an AST.
Shingling and BoS can work well in a traditional database or vector-based storage, providing a basis for cosine similarity, Euclidean distance, or other metrics to compare ASTs.

4. Path-Based Encoding
Node-Path Encoding: For each node in the AST, generate a path from the root node to the given node, capturing node types or labels along the path. Aggregate these paths as features.
Tree Path Hashing: Hash or encode paths from the root to leaf nodes, capturing the structure without needing machine learning. Then, store these path hashes as sets for each AST and use techniques like Jaccard similarity to compare sets between ASTs.
Path-based encodings allow for flexible and compact representations, supporting fast comparisons based on path similarity.

5. Vectorization Based on Token Sequences
Sequential Encoding: Flatten each AST into a sequence based on a predefined traversal order (e.g., preorder, postorder) and treat this sequence as a feature. You could then use simple tokenization (like n-grams or sliding windows) to generate vector features based on sequence similarity.
Subtree-Based n-Grams: Create n-grams of nodes or small subgraphs and count their occurrences as features, similar to n-gram models in text processing.
Using sequential encoding or subtree n-grams gives a straightforward way to vectorize ASTs, allowing you to apply traditional similarity search.

Implementation Workflow Without Neural Networks
AST Parsing and Feature Extraction:

Parse each AST and generate feature vectors using one of the methods above (e.g., path-based encoding, BoS, or shingling).
Storage in Vector or Document Database:

Store the feature vectors in a vector database (e.g., Milvus or ElasticSearch) to support similarity search, or use a document database with cosine similarity functions for vector comparison.
Similarity Search:

Use similarity measures (like Jaccard similarity for set-based representations or cosine similarity for vectorized forms) to find ASTs that are close in structure to a query AST.
This approach provides an efficient, non-neural network-based solution for AST similarity search, leveraging handcrafted structural and syntactic features to support scalable comparisons across a large database.

They are optimized for efficient Approximate Nearest Neighbor (ANN) search, which is ideal when you need quick, approximate matches within large datasets.
SQLite: As a relational database, SQLite is not optimized for vector-based similarity search. It stores data in tables and can perform filtering and exact matching well, but it doesn’t support native distance metrics for high-dimensional vectors. To approximate this functionality, you would need to implement custom distance calculations in SQL, which can be very slow for large datasets.
2. Scalability and Performance
Vector Database: Vector databases are built to handle large-scale vector data with optimized indexing structures like Hierarchical Navigable Small World (HNSW) graphs, tree-based indexing, or product quantization. They can handle millions of vectors efficiently, making them highly scalable.
SQLite: SQLite is a lightweight, single-file database designed for small to moderate workloads. While you could theoretically store vectors in SQLite and index them, the performance will degrade significantly as the dataset grows, especially with complex queries. SQLite also lacks parallel processing capabilities, making it slower for large-scale operations.
3. Indexing and Storage
Vector Database: Vector databases support specialized indexes for fast retrieval (e.g., HNSW, IVFPQ), making it possible to search through millions of high-dimensional vectors quickly. These indexes are optimized for approximate searches, which is often sufficient for similarity search applications.
SQLite: While SQLite supports basic indexes (B-trees and others), it doesn’t support indexes optimized for high-dimensional vector search. Implementing similarity search in SQLite would likely require storing vectors as individual rows or JSON fields and performing brute-force comparisons, which are computationally expensive.
4. Data Retrieval and Query Complexity

Vector Database: Designed to retrieve similar vectors quickly, vector databases allow you to query by similarity in a single, efficient step. This makes them well-suited for use cases requiring real-time similarity queries.
SQLite: While SQLite can retrieve records based on traditional relational queries, querying for high-dimensional similarity would require custom functions and extensive computational overhead, which can lead to slower retrieval times, especially as data size increases.
5. Use Case Suitability
Vector Database: Best for applications where similarity search is the primary goal, such as recommendation systems, image or document retrieval, and AST similarity search in your case. Vector databases are optimized for this and often provide high scalability with minimal setup.
SQLite: Suitable for applications with smaller datasets where similarity search is not critical. It’s effective for exact matching, simple key-value storage, and lightweight data applications.
When to Use Each Option
Use a Vector Database if similarity search is central to your application, as it will allow you to scale and retrieve similar items efficiently even with millions of entries.
Use SQLite if you have a small dataset and only occasionally need to retrieve similar vectors. For example, if your primary need is exact lookups and the similarity search is not frequent or performance-critical, SQLite might suffice, albeit with more complexity.
In summary, while SQLite could technically store vectors, a vector database is purpose-built for your AST similarity search use case, allowing it to handle large-scale, high-dimensional similarity queries with efficiency and speed.

can vector database find similar vectors across all stored data?

Yes, vector databases are specifically designed to find similar vectors across all stored data efficiently. They enable similarity searches by comparing a query vector to all stored vectors and returning the closest matches, which makes them ideal for tasks like recommendation engines, image retrieval, document similarity, and AST similarity search. Here’s how they accomplish this:

1. Approximate Nearest Neighbor (ANN) Search
Vector databases typically use ANN algorithms to perform similarity searches, which approximate the nearest neighbors of a query vector within the dataset. ANN algorithms are optimized to quickly find vectors that are close to the query vector in high-dimensional space without scanning every single vector in the database.
Common ANN indexing methods include Hierarchical Navigable Small World (HNSW) graphs, inverted file systems with product quantization (IVFPQ), and KD-trees. These structures make it possible to perform similarity searches across millions of vectors in a fraction of the time it would take to perform a brute-force comparison.
2. Distance Metrics for Similarity Search
Vector databases use distance metrics like cosine similarity, Euclidean distance, dot product, or Manhattan distance to determine how similar two vectors are. These metrics help identify the most similar vectors to a given query, enabling direct comparison across all stored vectors.
By storing vectors in specialized data structures and using optimized distance calculations, vector databases can retrieve the top-n most similar vectors to any query, even if the dataset contains millions of entries.
3. Efficient Indexing and Parallel Processing
Vector databases use indexes that are specifically tailored for vector-based searches. For example, HNSW and IVFPQ indexes enable the database to divide the vector space into smaller regions, allowing it to quickly focus the search on the relevant parts of the dataset.
They also often support parallel processing, which allows similarity queries to be distributed across multiple cores or even machines, further enhancing the search speed.
4. Real-Time Similarity Search
Because of these optimizations, vector databases support real-time similarity search. You can add a new vector and immediately perform similarity searches across the entire database, allowing for up-to-date comparisons and recommendations.
5. Flexibility and Scalability
Vector databases are highly scalable and can store millions or even billions of vectors, maintaining search efficiency even with large datasets. This makes them well-suited for large applications where similarity search is essential.
Summary
In essence, vector databases are designed precisely to find similar vectors across all stored data quickly and efficiently. The ANN search capability combined with high-performance distance metrics and optimized indexing structures ensures that similarity search in a vector database is both fast and scalable, even with large datasets.

In Milvus, you can search for the top similar vectors to each stored vector by iteratively querying the database in batches. Here’s a step-by-step outline:

Fetch All Stored Vectors:

Retrieve the IDs and embeddings for all vectors in the collection. In Milvus, this can be done by performing a range query.
Search Each Vector Against All Others:

For each vector, perform a similarity search in the collection. Set a limit to specify how many similar vectors to retrieve per vector (e.g., top 10).
Filter Out Duplicates or Self-Matches:

Since each vector will be similar to itself, ensure that self-matches are excluded from the results. You can do this by filtering out results where the id of the query vector matches the id of the result.
Here’s an example in Python:

python
Копировать код

# Assume collection is already loaded and indexed
collection_name = "ast_vectors"
collection = Collection(collection_name)

# Define similarity search parameters
search_params = {"metric_type": "COSINE", "params": {"ef": 50}}

# Dictionary to store the similarities for each vector
all_similarities = {}

# Perform similarity search for each vector
for vector in vector_data:
    query_vector = vector["embedding"]
    query_id = vector["id"]

    # Search for similar vectors
    results = collection.search(
        data=[query_vector],

Benefits:

Structured data and schema: SQLite provides a structured schema, ideal for indexing well-defined AST properties.

Challenges:

Hierarchical Data Storage: Representing tree structures in a relational format can be challenging. Solutions like adjacency lists or nested sets may be necessary but add complexity.

Scalability Constraints: SQLite may be inefficient for very large datasets, especially in terms of parallel access, as it doesn’t support concurrent writes well.

Storage: Store ASTs as JSON, leveraging SQLite’s JSON1 extension to store, retrieve, and filter JSON data.
Indexing: Use JSON indexing for specific AST properties, or custom indexes on frequently searched attributes.
Similarity Search: Limited, as SQLite lacks native capabilities for efficient tree matching or similarity searches on JSON structures. Custom solutions (such as hashing specific nodes and sub-trees) might be necessary.

Document Model: MongoDB’s JSON-like structure (BSON) supports nested documents and arrays, ideal for ASTs.

No Transactional ACID Compliance Across Multiple Documents: Although MongoDB offers multi-document transactions, its ACID compliance is not as strict as RDBMS.
Query Complexity for Large Datasets: Complex queries or aggregation pipelines over very large datasets can become computationally heavy.
Memory Usage: MongoDB’s BSON storage can lead to higher memory usage compared to other NoSQL databases (e.g., if large ASTs need to be decomposed into separate documents).
